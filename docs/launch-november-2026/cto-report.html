01 / Executive assessment

The November model is not yet the model implemented in the checked-in app. A terminology change from points to stamps is insufficient. Earning, identity, redemption, reward inventory and campaign eligibility need coordinated implementation and verification.

Evidence boundary: this report reviews local repository source on 22 October 2026. No live Supabase configuration, production authorisation, customer records or production transactions were tested. November is a target month; no launch date or engineering completion is certified.

04 / Implementation specification

Purchase and stamp ledger

  • Use immutable earning, redemption and reversal events. Record customer, shop, actor, purchase reference, timestamp, rule version and a unique request key. Treat this as a proposed data design, not the existing schema.
  • Staff confirms the purchase after identifying the customer. The server checks eligibility and staff permissions, then records one purchase award. Retrying the same request must return the existing result.
  • Keep village stamps and each shop’s card stamps separate. A single purchase can satisfy both only when it meets that card’s published conditions.
  • Handle refunds through linked reversal events and an approved policy for stamps already spent. Never delete history to make a balance look correct.

Reward claim and fulfilment

  • Each offer needs a contributing business, item, stamp price, conditions, stock or quota, valid dates and collection instructions. Merchants manage only their own offers.
  • Agree reservation timing. Recommended: reserve stock and spendable stamps at claim creation, release on expiry, and finalise once at collection. Keep available, held and spent amounts distinct.
  • Validate code expiry, customer ownership, authorised fulfiller, balance and inventory on the server. One-use codes cannot be replayed. A fulfilled claim retains its original terms.
  • Withdrawn or exhausted offers cannot accept new claims. Honour accepted claims or apply a documented cancellation/refund process.

Campaign and reporting

  • Count distinct eligible participating shop IDs within approved campaign dates, using Australia/Melbourne boundaries. Do not count scans, check-ins or refunded purchases as qualifying purchases.
  • Redemption does not erase campaign purchase history. A qualifying-purchase reversal may change eligibility under the published campaign rules.
  • Provide personal progress towards six shops. A ranked leaderboard is not necessary for the proposed draw.
  • Trader reporting must be shop-scoped. Association reporting should use appropriate aggregate measures. Do not expose individual cross-shop customer histories to every trader.

06 / Migration and release sequence

  1. Approve open policies and catalogue readiness; inventory the deployed database without treating checked-in SQL as deployment proof.
  2. Implement and test in an isolated environment. Do not rename historical points into stamps at 1:1 without an explicit conversion decision.
  3. Snapshot existing balances, classify demo versus real activity and rehearse the approved conversion with a reconciliation report.
  4. Update app, reporting, homepage, trader presentation, decals and terms together. Update service-worker caches when cached assets change.
  5. Run a staffed rehearsal with founding traders. Release only after owners sign off the evidence above.
  6. Monitor awards, claims and support issues. If integrity fails, pause affected writes and preserve the ledger; do not restore an old database over new transactions without reconciliation.
